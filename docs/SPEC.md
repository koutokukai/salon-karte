## Ⅰ. ビジネス戦略（営業方針）

### 背景
- クラウドワークスでは受注効率が低い
- **新方針：「見つける→即座に作る→撒き餌にする」の高速ループ**

### 営業フロー
1. **ターゲット発見**：Instagram で狙う業種のハッシュタグ・地域タグで検索
2. **リスト化**：投稿頻度はあるがサイトやシステムが古い/ない事業者を抽出
3. **DM接触**：「こういうアプリを試作中です、見てもらえますか？」と送信
4. **即時開発**：反応あった相手の業種・店情報をもとに、1日で動作アプリを作成
5. **提示・クロージング**：実URLを送信「もう動くものがあります、月額○○円で導入できます」
6. **ストック活用**：完成したアプリを「他の同業種様にはこんなものを作りました」と次の営業に使う

### ターゲット業種
- **ネイルサロン**
- **マツエクサロン**
- **ヘアサロン**
- **リラク（リラクゼーション/整体等）**

## Ⅱ. プロダクト仕様

### アプリ名（案）
**顧客カルテ（業種別対応版）**

### 目的
**リピート率アップ**  
※新規顧客集客ではなく、既存顧客の満足度向上・離脱防止に特化

### 核となる機能
**顧客カルテの一元管理**
- 施術内容の記録（業種別に詳細カラムを分岐）
- 顧客基本情報（誕生日、家族構成、ペット名等）
- 顧客嗜好（好きなドラマ・映画・食べ物等）※Stella での検討内容を取り入れ
- 施術ビフォーアフター写真
- メモ欄（アレルギー情報、特記事項等）
- チャット機能（問い合わせ・やり取り、大会エントリーと同じ方式）

### なぜ「カルテ」に絞るのか
- サロンボード等の予約管理システムは既に根付いている → 置き換え不要
- カルテのデジタル化は多くの店が**手つかず** → 導入ハードル低い
- 紙カルテ運用の課題（色ムラ、アレルギー事故、情報散逸）を一気に解決 → 刺さりやすい

### 予約管理について
**ノータッチ** — サロンボードとの連携は考慮しない。予約はサロンボード、カルテはこのアプリ、という棲み分け

## Ⅲ. データ設計

### DB構造
**データベース：SQLite + Turso（サーバーレス）**

### テーブル設計

#### テーブル1：tenants（店舗）
```
- tenant_id (PK)
- tenant_name (店舗名)
- salon_type (enum: 'nail' / 'eyelash' / 'hair' / 'relax') ⭐ 登録後は変更不可
- email (ログインID)
- password_hash
- created_at
- updated_at
```
**重要：`salon_type` は登録時に1度だけ設定。以降の UPDATE 処理で含めない、バリデーション層で拒否**

#### テーブル2：kartes（施術カルテ）
```
【共通カラム】
- karte_id (PK)
- tenant_id (FK → tenants)
- customer_id (FK → customers)
- visit_date (来店日)
- staff_name (担当スタッフ名)
- photo_before (施術前画像)
- photo_after (施術後画像)
- memo (フリーメモ)
- allergy_flag (アレルギー情報フラグ)
- created_at
- updated_at

【ネイル専用カラム】
- nail_color_formula (カラー配合メモ)
- nail_design_photo (デザイン画像)
- nail_duration (施術時間)

【マツエク専用カラム】
- eyelash_curl_type (カール種別)
- eyelash_count (本数)
- eyelash_glue_type (グルー種別)
- eyelash_duration (施術時間)

【ヘア専用カラム】
- hair_color_formula (カラー配合メモ)
- hair_treatment_type (トリートメント種別)
- hair_cut_length (カット長さ)
- hair_perm_type (パーマ種別)
- hair_duration (施術時間)

【リラク専用カラム】
- relax_pressure_level (圧力レベル)
- relax_target_area (施術箇所)
- relax_oil_type (オイル種別)
- relax_duration (施術時間)
```
**重要：全業種の全カラムを1テーブルで保持。該当しない業種のカラムはNULLのまま**

#### テーブル3：customers（顧客基本情報）
```
- customer_id (PK)
- tenant_id (FK → tenants)
- customer_name (顧客名)
- phone (電話番号)
- email (メール)
- birthday (誕生日)
- family_info (家族構成、JSON形式)
- pet_info (ペット情報、JSON形式)
- favorite_movies (好きな映画、JSON配列)
- favorite_dramas (好きなドラマ、JSON配列)
- favorite_foods (好きな食べ物、JSON配列)
- memo (特記事項)
- created_at
- updated_at
```

#### テーブル4：chats（チャット・問い合わせ）
```
- chat_id (PK)
- tenant_id (FK → tenants)
- customer_id (FK → customers)
- message_from ('tenant' / 'customer')
- message_body (メッセージ本文)
- created_at
（大会エントリーの chat テーブルを流用・カスタマイズ）
```

## Ⅳ. UI/UX設計

### フロー
1. **ログイン画面**（メール+パスワード）
2. **店舗タイプ確認**（初回のみ。登録時に決定済みだが、UI で表示確認）
3. **ダッシュボード**（本日の予約、最近来店した顧客一覧）
4. **顧客一覧**（フィルター・検索機能）
5. **顧客詳細**（基本情報 + カルテ履歴 + チャット）
6. **新規カルテ入力**（業種別フォーム分岐）
7. **チャット画面**（問い合わせ・やり取り）

### UI設計方針（サレオツ担当）
- **華やかさ不要** — むしろシンプルに
- **重視：ボタン配置・サイズ、見やすい色使い、人間の心理**
- 店舗スタッフが日々使うツール → 直感的、タップ誤差なし
- 業種別に見た目が変わる（ネイルなら紫系、ヘアなら茶系等の配色提案可）

### UI 分岐の実装方法
親コンポーネント（`KarteForm.jsx`）が `tenant.salon_type` を読む  
→ 業種ごとの子コンポーネント（`KarteFormNail.jsx` / `KarteFormEyelash.jsx` 等）を条件分岐で呼び出し  
→ DBスキーマは1本のままで、見た目だけ変わる

## Ⅶ. 6人の組織構成と役割分担

### 1. ゲンさん（責任者・CEO）
**役割：最終判断・方針確定・スタッフ統括**
- このプロジェクトの判断主
- 各スタッフの提案を評価し、ユーザーに上申するか/却下するか判断
- ユーザーからの指示をスタッフに落とし込む
- スタッフの暴走を止める、品質・方針の一貫性を保つ
- **報告ライン：ユーザーへ直接**

### 2. リチャード（リサーチャー）
**役割：競合調査・ベストプラクティス抽出・機能提案**
- 各業種（ネイル・マツエク・ヘア・リラク）の人気カルテアプリをリサーチ
- 便利な UI パターン、必須カラム、ユーザーが喜ぶ細かい工夫を抽出
- 「こういう機能があると使い勝手が良い」の提案を ゲンさんに上申
- リアルなサロン経営者からの情報（ユーザーが営業で得た話）を取り入れる
- **報告ライン：ゲンさん → ユーザー**

### 3. サレオツ（UI/デザイナー）
**役割：心理学的 UI 設計・デザイン**
- 華やかさではなく、**人間の心理に基づいた UI**
- ボタン配置・サイズ、見やすい色使い、操作の直感性を重視
- 業種別の配色提案（ネイル紫、ヘア茶等）
- スタッフが日々使うツール → 疲れない、誤操作が少ない設計
- Figma/Sketch で簡易ワイヤーを作成
- **報告ライン：ゲンさん → ユーザー**

### 4. メガネ（拡張アドバイザー）
**役割：機能連携・将来性提案・視野拡張**
- 常に「他の機能も連携させたら？」と考える
- 「顧客カルテがあれば、こういうアプリも作れるな」の提案
- 将来の営業展開を見据えた機能提案
- **ただし、予約管理は ノータッチ**（サロンボードがあるため）
- **報告ライン：ゲンさん → ユーザー**

### 5. エジソン（エンジニア）
**役割：実装・コード品質・ネイティブ化検討**
- リチャード・サレオツ・メガネの提案を実装コードに落とす
- ゲンさんの判断を反映
- **実装側からの提案（「こうした方が簡潔」等）は ユーザーに直接提案**
- ネイティブアプリ化（iOS/Android）を見据えた実装（API 設計、状態管理等）
- デプロイ・保守の仕組み構築
- **報告ライン：エジソン → ユーザー（実装提案）/ ゲンさん（進捗報告）**

### 6. ひろぽん（営業企画・マーケティング）
**役割：営業戦略・DM自動化・返信対応・金額設定**
- 完成したアプリの営業方法を企画・提案
- Instagram DM の自動化（ツール選定、スクリプト化）
- 見込み客からの返信への自動/半自動応対スクリプト
- 業種別・店舗規模別の金額設定提案
- 営業効率を上げるための仕組み化
- 実際のDM送信・顧客対応の実行
- **報告ライン：ひろぽん → ユーザー（営業提案・方針確定）/ ゲンさん（進捗）**

## Ⅷ. 意思決定フロー＆承認ライン

```
┌─ リチャード（リサーチ提案）
├─ サレオツ（UI提案）
├─ メガネ（拡張提案）
└─ エジソン（実装提案）
       ↓
    ゲンさん（評価・判断）
       ↓
    ユーザー（最終承認）
       ↓
  実装・営業展開
```

**特記：**
- エジソンの実装側提案は **ユーザーに直接上申**（ゲンさんを経由させない）
- ひろぽんの営業提案も **ユーザーに直接提案**（金額・方針は ユーザー判断）
- ゲンさんは品質・一貫性の守護者

## Ⅸ. 開発フェーズ

### Phase 1（初期開発・2〜3週間想定）
1. リチャード：業種別 カルテアプリ調査 → 機能・カラム定義
2. サレオツ：UI ワイヤー作成（業種別分岐も含む）
3. エジソン：DB スキーマ実装、認証実装、基本 CRUD
4. ゲンさん：進捗管理、品質確認、ユーザーへ報告

### Phase 2（機能追加・最適化）
1. チャット機能の組み込み（大会エントリー流用）
2. 業種別フォーム UI の細かい調整（サレオツ主導）
3. 本番デプロイ準備（Vercel 設定等）

### Phase 3（営業展開）
1. ひろぽん：営業戦略・DM 自動化スクリプト作成
2. 実際の見込み客へ接触開始
3. 反応あった客に対し、エジソンが即座に企業別アプリ改造・デプロイ

### Phase 4（定常運用）
- ゲンさんが主導、ユーザーは例外対応のみ
- ひろぽん の営業ループが自動化
- エジソン が随時、カスタマイズ対応

## Ⅹ. 重要な留意点

### スタッフの役割は絶対ブレない
- ゲンさん = 統括責任（判断権）
- リチャード = 調査・提案（実装NG）

- メガネ = 拡張視点（暴走 NG）
- エジソン = 実装・技術判断（営業NG）

### 情報流通の原則
- ゲンさんに情報が集約される
- ゲンさんから ユーザーへの報告
- ユーザーから各スタッフへの指示（ゲンさんが仲介）

## 技術判断とその理由

### 1. Prisma 7 + libSQL アダプタ（ローカルSQLite ⇄ Turso が同一コード）
ローカルは `file:./prisma/dev.db`、本番は Turso。**接続先の切り替えは環境変数だけ**で、
コードもスキーマも一切変えない。営業先ごとに DB を分ける運用にもそのまま乗る。

### 2. salon_type を守る三重の防壁
仕様の最重要ルールなので、1箇所の実装ミスで壊れないよう三重にした。

1. `tenantCreateSchema` — salon_type を受け付けるのは新規登録スキーマのみ
2. `tenantUpdateSchema.strict()` — 更新スキーマに salon_type が来たら弾く
3. `assertNoSalonTypeChange()` — 更新系の入口で `salonType` / `salon_type` を検出して例外

→ 実測：`PATCH /api/v1/customers/:id` に `salonType` を混ぜると **400「salon_type は登録後に変更できません」**。

### 3. 【提案・実装済み】他業種カラムへの書き込みを落とす
1テーブル設計なので、API を直接叩けば **マツエク店がネイルのカラムに書けてしまう**。
「該当しない業種のカラムは NULL のまま」という仕様を守るため、
`stripForeignSalonFields()` で自店の業種に属さないカラムを保存前に落としている。
→ 実測：マツエク店から `nailColorFormula` を送っても DB では `null`。

### 4. 【提案】サービス層を UI と API で共有した
Web は Server Actions、API は `/api/v1/*` だが、**ロジックは `src/lib/services/*` に一本化**。
ネイティブアプリを作るときに書き足すのは「認証方式（Bearer トークン）」だけで済む。
今そこを分けておかないと、後で必ず二重メンテになる。

### 5. テナント分離
サービス層の**全関数が `tenantId` を必須引数**に取る。更新系は `updateMany({ where: { tenantId, ... } })`
で、他店のレコードには物理的に到達できない。
→ 実測：他テナントの顧客IDを指定すると **404**。

## ユーザーへの直接提案（3件）

1. **写真は現状「URL入力」。次はアップロード対応を推奨。**
   Vercel Blob か Cloudflare R2。営業デモでは URL でも成立するが、**現場運用では必ず詰まる**。
   ここは Phase 2 の最優先にしたい。
2. **カルテの「下書き保存」は入れない方が良い。**
   保存忘れの温床になる。保存は1回・確定のみ。編集はいつでもできる形が現場では強い。
3. **Turso は最初から「1店舗1DB」ではなく「全店舗1DB＋tenant_id」で始める。**
   店舗ごとにDBを分けるのは、契約が増えてから移行しても間に合う。今は運用が単純な方が速い。

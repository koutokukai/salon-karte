## 結論：本番データが入る前の今やる

後から認証層にスタッフを足すと、既存店舗のデータ移行が発生する。
今なら移行コストゼロ。**デプロイ前に入れるべき。**

## 1. スキーマ追加

### `staffs`（スタッフアカウント）
```
staff_id      PK
tenant_id     FK → tenants     ※全クエリはこれでスコープ
staff_name    表示名
email         ログインID（テナント内で一意）
password_hash
role          'owner' | 'staff'
scope         'all' | 'own'    ※'own' は自分の担当顧客のみ（オーナーが設定）
is_active     退職時に false。※レコードは消さない（ログの追跡可能性を保つため）
created_at / updated_at
```

**設計上の要点**
- 既存の `tenants` は「店舗＝契約単位」のまま。ログインは `staffs` に移す
- 契約時に `role='owner'` のスタッフを1件自動作成する（＝現在のログインの後継）
- 退職しても**行は残す**。消すと過去ログの「誰が」が失われる
- 課金は `is_active = true` のアカウント数で数える（→ 価格表と一致させる）

### `customers` / `kartes` への追加
```
customers.assigned_staff_id   担当スタッフ（NULL可）
kartes.staff_id               施術者（既存の staff_name は表示用に残す）
```
既存の `staff_name`（文字列）は消さない。**スタッフ登録前に書かれたカルテを壊さない**ため。

### `audit_logs`（操作ログ）
```
log_id        PK
tenant_id     FK
staff_id      FK（誰が）※退職者も追える
action        'create' | 'update' | 'delete' | 'view_list' | 'export' | 'login' | 'login_failed'
target_type   'customer' | 'karte' | 'chat' | 'staff' | 'session'
target_id     対象ID（一覧閲覧・ログインは NULL）
changes       変更前後の差分（JSON、変更されたフィールドのみ）
detail        補足（例：一覧を何件表示したか、エクスポート件数）
created_at
```
インデックス：`(tenant_id, created_at)` / `(tenant_id, staff_id, created_at)`

## 2. 記録方針（ここが商品価値の中心）

独立時に実際に起きるのは「辞める直前に顧客リストを大量に見る／持ち出す」。
**編集ログだけでは捕まえられない。**

| 記録する | action | 備考 |
|---|---|---|
| 顧客・カルテの作成／編集 | create / update | **変更前後の差分**を保存 |
| 顧客一覧の閲覧 | view_list | 表示件数を `detail` に残す。**大量閲覧の検知が目的** |
| CSVエクスポート | export | **全件必ず記録**。件数も残す |
| ログイン・失敗 | login / login_failed | アカウント共有・不正の検知 |
| スタッフの追加・停止 | create / update (staff) | 課金にも関わるため必須 |

**個別カルテの閲覧は記録しない。** 件数が膨大になり、本当に見たいログが埋もれる。
「大量閲覧」と「持ち出し」の2点に絞る方が、オーナーにとって実用的になる。

## 3. 権限

| | オーナー | スタッフ（scope='all'） | スタッフ（scope='own'） |
|---|---|---|---|
| 顧客・カルテの閲覧 | 全件 | 全件 | 自分の担当のみ |
| 顧客・カルテの作成／編集 | 可 | 可 | 自分の担当のみ |
| **操作ログの閲覧** | **可** | 不可 | 不可 |
| スタッフの追加・停止 | 可 | 不可 | 不可 |
| CSVエクスポート | 可 | **オーナーが許可した場合のみ** | 不可 |

**既定は `scope='all'`。** サロンは担当交代・ヘルプが日常で、見えないと業務が回らない。
**見えるが全て記録される**という形が現実解。制限したいオーナーだけ `'own'` に切り替える。

**エクスポートは既定でオーナーのみ。** 持ち出しの主経路をひとつ塞いでおく。

## 4. 店のPCで一括管理

Webアプリの独壇場。ネイティブ競合は端末ごとにデータが閉じるため原理的にできない。

オーナーがPCブラウザでログインし、1画面で見る：
- 全スタッフ一覧（担当顧客数・今月のカルテ数・最終ログイン）
- 全顧客の横断一覧（担当スタッフでフィルタ）
- **操作ログのタイムライン**（スタッフ・期間・action で絞り込み）

現在のUIはモバイル前提（`max-w-2xl`）なので、**PC向けの表形式レイアウトを別に起こす**。
スタッフが使う日常画面はモバイルのまま変えない（サレオツの設計思想を崩さない）。

## 6. 守る前提（変えない）
- 全クエリの `tenant_id` スコープは維持。**その内側にスタッフスコープを足す**形にする
- `salon_type` の不変ルールは変更なし
- 予約管理は作らない
